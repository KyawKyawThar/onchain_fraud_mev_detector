# Production Readiness — MVP → GA

**Companion to** [ARCHITECTURE.md](ARCHITECTURE.md). The MVP build-out delivers a *demonstrable* platform. This document defines what separates that from a **production-grade, sellable, legally-defensible** platform — and the path to get there.

**Production bar (assumed):** a commercial compliance/risk-intelligence SaaS with paying enterprise customers, where alerts and risk scores carry legal/financial weight, inputs are adversarial, and the audit trail is evidence. If the real bar is lower (internal tool, single trusted user), drop the compliance and multi-tenant epics.

---

## The core reframe

> Production-grade is **not a later phase**. For this system, certain properties must be built into every MVP increment; others are a distinct hardening effort that can only happen once the system exists end-to-end.

### Bucket 1 — Shift-left (build into the MVP increments; do NOT defer)

These are correctness properties of the data path. Retrofitting them = rewriting the path. Each is tagged with where it belongs in the build-out.

| Non-negotiable | Why it can't wait | Built with |
|---|---|---|
| **Idempotent consumers** — dedup replayed/duplicate events by key | At-least-once delivery is the baseline; a non-idempotent projection is corrupt the first time Kafka redelivers | every consumer, as it's built |
| **Reorg rollback** in any service holding derived state (§15) | A `BlockReverted` handler bolted on later means auditing state you can't trust | the same increment that adds the state |
| **revm sandbox + gas/step caps** (§7 hardening) | Honeypot bytecode is hostile input by design — an unsandboxed worker is an RCE, not a bug | the simulation service |
| **Audit completeness** — every state change is an event in the store (§2, §4) | The legal claim ("complete, replayable trail") is void if any path mutates state without emitting | every event-producing service |
| **Commands stay off the event store** (§2) | The audit log must record facts, not attempts; fixing this later means rewriting history | the simulation dispatcher |
| **`provisional` flag until finality** (§15) | Customers must distinguish unconfirmed from confirmed from day one (§11 WS contract) | every alert-producing service |
| **Deterministic replay** — replay a window → identical events (§18) | This *is* the backtest/audit guarantee; non-determinism discovered late is unfixable cheaply | the whole MVP path |
| **AuthN/Z on every endpoint**, event-store append internal-only (§4) | "Add auth later" always leaks; the append API is the integrity boundary | each public/ingest surface |

If these aren't true at the end of each increment, that increment isn't done. **This is the single most important change vs. an MVP mindset.**

### Bucket 2 — Hardening epics (gate to GA; can't be done until the system exists)

Run these *after* the MVP path is green, sequenced by the exit gates below — not by calendar.

## Hardening Epic A — Reliability & failure correctness

**Goal:** the system behaves correctly when infrastructure and inputs misbehave, and that's *proven*, not assumed.

- [ ] **Chaos / fault injection harness:** kill workers mid-revm, drop Kafka brokers, partition the network, replay duplicate + out-of-order events, force deep reorgs. Assert projections converge to the correct state.
- [ ] **HA for every stateful component:** Kafka replication factor ≥3, RabbitMQ quorum queues across nodes (§20), ClickHouse replicated, Postgres primary + sync replica with automated failover, Redis HA/sentinel.
- [ ] **Graceful degradation:** if simulation backlogs, provisional alerts still flow (fast path independent of slow path, §6). If intelligence is down, API serves stale-but-flagged cache.
- [ ] **Resilience primitives everywhere:** timeouts, retries with jitter, circuit breakers (already on the RPC pool §5 — extend to all gRPC/HTTP hops), bounded channels verified to apply backpressure end-to-end (§17).
- [ ] **DLQ operations:** `sim.jobs.dlx` drain + replay runbook; alert on DLQ depth (§7).
- [x] **Consumer-lag & gap detection (lag half, 2026-07-19):** every durable Kafka consumer is built through `event_bus::lag::build_reporting_consumer`, exporting the per-partition `kafka_consumer_lag` gauge; every consume loop parks unprocessable records on its own `mev.dlq.<consumer>` topic (`Handled::Skip` + poison), and every binary serves `/livez` + `/readyz` (`telemetry::health`, `HEALTH_ADDR`). The `RuleCreated` dual-write went through a transactional outbox (`rule_outbox` + `rule_engine::outbox`). The dashboards/alerts on this signal (`kafka_consumer_lag` panel + `KafkaConsumerLagHigh` alert) shipped in Sprint 13 t4, 2026-07-19. Still open: event-store sequence-gap detection — a distinct correctness feature, not an observability wire-up.

**Exit gate:** chaos suite passes; killing any single node loses no audit history and recovers within RTO.

## Hardening Epic B — Disaster recovery & data integrity

**Goal:** you can rebuild the entire system from the source of truth, and you've actually done it.

- [x] **Backups + tested restore (2026-09-05):** [`docs/runbooks/backup-restore.md`](docs/runbooks/backup-restore.md), backed by [`crates/backup/`](crates/backup/) — a snapshot/restore/drill tool for Postgres and ClickHouse (the event store's `events` table included), plus the `backup serve` agent that runs both on a timer. **The control is the restore, not the dump.** A cron'd `pg_dump` and a runbook page is a belief with infrastructure attached: nothing in it ever reads the artifact back, so its first real execution is during the incident. The failure modes are not exotic — a dump taken while the database was being written to, a dump missing the table someone added in March, a client too old to read the server, an artifact whose bytes rotted six weeks ago — and they share one property: **every one of them passes a check that the backup job exited zero.** So `drill` restores the newest *real* artifact into a throwaway database it creates and drops, re-fingerprints it, and compares. **The mechanism that makes that meaningful is that the fingerprint is taken inside the dump's own cut:** `pg_export_snapshot()` handed to `pg_dump --snapshot=<id>` means the manifest describes *the bytes*, not the database at a nearby instant, so a drill against a live, busy database is exact rather than flaky — and a flaky drill is a drill that gets switched off. ClickHouse's log gets the same guarantee from the `appended_at < W` watermark `crates/rebuild` already established; its derived tables are fingerprinted from the streaming rows as they are written, which is honestly labelled as the weaker cut it is. **Non-destructive, therefore on a timer** — nothing is stopped and no window is needed, which is the actual fix for "backups go untested". **Tables are discovered, never listed:** a hand-maintained table list is a backup that silently stops covering the next table anyone adds and looks green the whole time. **Two traps found and closed in the build:** a ClickHouse materialized view is an insert trigger, so restoring `events` while the view exists double-writes the rollup that was also restored (tables → data → views, asserted in a test); and a merging engine's raw rows collapse in background merges, so both sides read `FINAL` or the drill fails at random. **RPO/RTO are measured, not declared:** RPO is the age of the newest artifact *that a recent drill has shown to be restorable* — a stale drill breaches on its own, even while snapshots land on schedule — measured from the **cut**, not from when the dump finished; RTO is the drill's own wall clock against today's data volume plus a **separately reported, human-declared** orchestration overhead, because a measurement and an estimate added together and presented as one measurement is how RTOs come to be wrong by an order of magnitude. Both are exported as `budget` and `measured` series so the alert rules (`BackupRpoBreached`, `BackupDrillStale`, `BackupDrillFailing`, `BackupAgentAbsent`) hard-code no thresholds. The agent is a **Deployment, not a CronJob**, for the same reason the gauges are ages: a CronJob cannot report that it did not run. `just backup-drill-test` proves the whole path against real Postgres and real ClickHouse in CI. **A design-review hardening pass followed (2026-09-05), and three of its findings were real bugs.** (1) The agent ran a multi-hour `pg_dump` **inline in a `select!` arm**, so for the duration of the longest operation the objective gauges could not be republished, `SIGTERM` was ignored, and `tokio::time::interval`'s default `Burst` would then fire every missed tick back-to-back. A backup agent whose RPO gauge freezes while Prometheus scrapes the stale value is the "monitoring the monitor" trap §15 names, self-inflicted. Now a 30s heartbeat publishes first and spawns work on its own task, and the trigger is **observed state** — *is the newest artifact older than the cadence?* — which is idempotent across restarts (the previous shape took a full `pg_dump` on every restart of a crash-looping pod, because `interval` fires its first tick immediately) and skips-and-counts rather than stacking overlapping runs. (2) The ClickHouse read-back had drifted from the dump: the copy used to *verify* a restore had lost the truncation check, so a connection cut mid-verification produced a short row count reported as a **divergence** — "your backup is bad" — when the truth was "the verification did not finish". Blaming the artifact for a transport fault is the worst thing a control can do; there is now one `stream_rows` and the check lives in it. (3) `db` and `thiserror` were dependencies the crate never used — added to satisfy arch-conformance's `sqlx`-needs-`db` rule rather than its *point*, which is that transient-vs-permanent classification is uniform. Failures are now typed `Transient`/`Permanent`/`Cancelled` (Postgres through `db::is_permanent`), so `backup_runs_total{outcome}` separates "ClickHouse blipped" from "no backup has been possible since the Postgres upgrade" and only the latter pages — well before the RPO budget would notice. Also in the pass: `Destination { database, scratch: bool }` became a `Scratch` that only `provision_scratch` can construct and `drop_scratch` consumes **by value**, so dropping production or double-dropping does not compile and the runtime guard is gone; leaked scratch databases are cleaned by the **next** run's sweep (async `Drop` does not exist and `SIGKILL` runs no destructor, so the creation time lives in the database's own name); manifest notes became typed, so "this view's data is not in the artifact" is now an `is_complete()` that **fails the drill** and alerts, instead of prose in a log nobody reads; the trait split into a read-only `StoreReader` (`backup fingerprint` cannot restore or drop anything) and `BackupTarget`; and the source database is a manifest field rather than something parsed back out of `CREATE TABLE` text. Still open: **offsite replication is manual** (an `rsync`/`s3 sync` of `BACKUP_DIR`, checkable in place via the per-file SHA-256s, but not automated), and the drill restores to the **same server** — it does not prove a new one can be obtained, which is the multi-AZ item below.
- [x] **Projection rebuild runbook (2026-09-04):** [`docs/runbooks/projection-rebuild.md`](docs/runbooks/projection-rebuild.md), backed by [`crates/rebuild/`](crates/rebuild/) (the shared procedure) and [`simulation::rebuild`](crates/simulation/src/rebuild.rs) (the first implementation). §2's "projections are derived" is now a **test**, not a claim: `just projection-rebuild-drill` builds the read model the live way in throwaway Postgres + ClickHouse, rebuilds it from the event store, and asserts a byte-identical result. **Nothing is wiped.** The replacement is built in a **staging namespace** — a Postgres schema on the pool's `search_path` ([`db::connect_in_schema`](crates/db/src/lib.rs)), a ClickHouse database on the client — and swapped in. Staging as a *namespace* rather than a schema change is what lets the **unmodified production write path** target it, which is what makes "fold through the live consumer" achievable at all. Promotion is one transaction of `ALTER TABLE … SET SCHEMA` (Postgres DDL is transactional, so no reader sees half the tables swapped), and the superseded generation is **kept** — the only copy of any `lost` row, and the rollback. ClickHouse's `EXCHANGE TABLES` is pairwise and therefore **not** atomic across its two tables; stated rather than papered over, and tolerable because those are the trend surface, not the system of record. The consequence that matters: **`verify` is non-destructive and needs no `--yes`**, so the drill runs on a timer against production rather than needing an outage window — the difference between "proven once before GA" and a standing guarantee. **A correctness bug found in review and fixed:** the replay had no upper bound, so each per-type lane walked to whatever the tail was when *it* drained — a torn read belonging to no instant, reporting every event that arrived during the run as a phantom divergence. A rebuild now pins a **watermark** (`GET /v1/watermark`, from ClickHouse's own clock so host skew cannot widen the cut) and replays `[epoch, W)`, bounded on **ingest** time (`appended_at`) not event time — `occurred_at` is not monotonic with arrival, so an event-time bound is not a cut at all. The residual in-flight race is closed by **idempotent catch-up** (the consumer resumes from committed offsets behind `W`), not a longer lock, which is why restarting it is a step of the procedure. **The fold is the live fold:** `apply` drives the real `ProjectionConsumer::handle` with the broker removed, so a rebuild cannot drift from the path it validates. **"Byte-identical" covers derived columns only**, with the four exclusions named in one place (`…updated_at`, `incident_analytics.appended_at` — each `now()` at write, a clock rather than a projection); everything else, event-time watermarks included, is compared. Divergence is **classified** — `lost` / `gained` / `changed` — and each class names its rows, so a failure is a diagnosis rather than a hash mismatch. Metrics ship with it (`projection_rebuild_divergence_rows{class}`), because a divergence printed in a terminal is a number somebody read once. **Also the first measurement of a known debt:** the ClickHouse firehose can lose a row to a store fault between two writes of one event (recorded in `projection_consumer`'s docs), which now surfaces as a countable `gained` divergence instead of an unfalsifiable footnote. Still open: intelligence's Postgres store (labels/entities/attributions/sanctions) and its ClickHouse adjacency graph are not yet wired to the seam — risk scores are a cache over that store and follow it — which is the remaining work for the exit gate.

- [ ] **Multi-AZ deployment**; regional DR plan if SLA requires.

**Exit gate:** a full projection rebuild from the event store reproduces current state exactly; restore drill meets RTO. *(Rebuild half: the procedure exists, is proven on the simulation read model, and runs in CI — see above. Restore half: the drill exists, is proven against real Postgres and ClickHouse in CI, and measures the RTO rather than asserting one. Not met until (a) intelligence's store is wired to the rebuild seam, and (b) both drills have run once against production-scale data with the durations recorded as the RTO inputs — the numbers only mean anything at the volume they will be run at.)*

## Hardening Epic D — Scale, performance & SLOs

**Goal:** the latency budgets in the doc hold *under production load*, with headroom.

- [ ] **Define SLOs** (the doc names the panels, §19 — turn them into targets): end-to-end alert latency (block → notification), fast-path < 1s (§6) at p99 under load, API p50/p99, simulation confirmation rate, uptime. Every named panel now has a metric and a dashboard (Sprint 13 t4), and `deploy/prometheus-rules.yml` wires a first pass of alert thresholds — but they're explicitly provisional (seeded from the one hard number the source doc states, §6's <1s p99; everything else is a conservative placeholder with no production traffic to calibrate against). **Calibrated against the measured run (2026-09-11):** every threshold in `deploy/prometheus-rules.yml` now declares which of exactly three things it is — a **published claim** (§6's <1s, §19's <100ms), an **exported gauge** (the deployment's own config *is* the threshold, so the two cannot drift), or a **measurement** — and the file's header carries that taxonomy as its contract. What the calibration actually found was not mis-tuned numbers but **four rules that could not fire at all**, three of them the same defect class as the pre-2026-09-07 `FastPathLatencyHigh`. Every `_seconds` histogram shares `telemetry::metrics::LATENCY_BUCKETS_SECONDS`, whose top finite bucket is **10s**, and `histogram_quantile` reports the highest finite bound for a quantile in `+Inf` — so `AlertEndToEndLatencyHigh` (`> 30`) and `EmbeddingSweepLapTooSlow` (`> 21600`) were capped at 10 and had been green since the day they were written. The first moved to 5.0, the largest ladder rung that leaves the comparison decidable; the second could not be expressed on that ladder *at any threshold*, so the staleness SLI moved to a new unbucketed gauge (`intelligence_embedding_sweep_last_lap_seconds`), with a test asserting it is a Gauge carrying the real lap. The four **grounding-audit** rules read `increase(...[1d])` against a **weekly** CronJob: a one-day window over a seven-day cadence is blind six days in seven, and `increase()` needs two samples where a short-lived Job may be scraped once — now `max_over_time(...[8d])`. And the **token-budget** alarm cannot fire as shipped: `usage::budget::run` returns immediately when `USAGE_TOKEN_BUDGET` is unset, exporting no series, so absence silently satisfied both it *and* its own monitor-the-monitor rule; `CopilotTokenBudgetDisarmed` now closes that gap, and the counter whose doc comment says "alert on any non-zero rate" finally has one (`CopilotBackfillStragglers` — the loose end named in Epic E). Genuinely calibrated from the numbers: `FastPathQueueWaitHigh` 0.5 → **0.25** (0.5 was *exactly* the queue wait measured when the fast path hit its 1s ceiling, so the "leading indicator" led by nothing; healthy is 2.5ms), `ApiLatencyHigh` 1.0 → **0.5** to match `slo.json`'s `api_p99_seconds` — the run breached that budget while the alert sat green on a threshold twice as loose — a new `ApiErrorRatioHigh` for the 0.883 success ratio nothing was watching, and `DetectorLatencyBudgetExceeded` 0.25 → **0.05**, since 250ms was the *entire* measured healthy fast path. Six `severity: informational` placeholders were **deleted** (simulation confirmation rate, reorg frequency, two embedding-efficiency rules, two clustering-tuning rules): each attached an invented number to an *observation* rather than a fault, and would never have become an SLO however much traffic arrived. Five more were **promoted to `warning`** — they were structural all along (a count that should be zero, or two series that contradict each other) and only mislabeled. Exactly one informational rule survives, because over-retention is the argued milder failure rather than an unpicked number. **The calibration's most serious finding was not a number at all.** `deploy/k8s/base/infra/prometheus.yaml` carried its *own inlined copy* of the rules — justified when written as keeping the manifest tree self-contained — and it had drifted for three sprints. The copy was missing `FastPathQueueWaitHigh`, `FastPathSilent`, `ScreeningLatencyP50High` and the entire copilot, backup, embedding and clustering groups, and its `FastPathLatencyHigh` **still read `detector_detect_duration_seconds`**: the rewiring above was applied to the compose file and never to the one that actually runs in production, so the platform's headline SLO alert was fixed in review and left broken in the cluster. Prometheus in K8s now generates its rules from `deploy/prometheus-rules.yml` through a `configMapGenerator`, exactly as the Grafana dashboards already do for exactly this reason (`kustomize build` is already run with `--load-restrictor LoadRestrictionsNone`, so the reference resolves); the volume became a projected one to span the two ConfigMaps, and the generator's name hash is kept deliberately, since Prometheus does not watch its rule files and the hash change is what rolls the pod. Verified: both overlays build, and the generated ConfigMap carries all 43 alerts with no dangling references. A rule is environment-agnostic, so there was never a second version to maintain — only a second chance to be wrong. **Then the contract itself became a test (2026-09-11, second pass).** Everything above was written as prose at the top of a YAML file, and prose is precisely how four unfireable rules got there — so [`crates/alert-conformance`](crates/alert-conformance/) now parses `deploy/prometheus-rules.yml` and fails `cargo test` on a quantile threshold off its metric's ladder or above its ceiling, a batch-job series read through a window narrower than the job's cadence or through `increase`/`rate` rather than `max_over_time`, an unroutable severity, a *new* `informational` rule, a missing annotation, or a duplicate name. It is a sibling of `arch-conformance` in shape and in argument, and it is worth a crate for one reason: **an alert has no failing state.** Nearly everything else here announces its own breakage — a test reddens, a pod crash-loops, a type stops compiling — whereas a rule that cannot fire is indistinguishable from a healthy system, and green is what you were hoping to see. Verified by re-introducing the shipped `> 30` bug and watching the gate name both fixes. **The one-ladder assumption was the root cause and is fixed too:** `telemetry::metrics` now exposes `bucket_class`/`buckets_for` with a second `JOB_DURATION_BUCKETS_SECONDS` ladder (1s–1 day), because `_seconds` does not distinguish "how long did this call take" from "how long until this comes round again" — and three metrics beyond the two alert bugs were silently pinned at 10s, including **`predictive_liquidation_lead_time_seconds`, the §19 signal for the predictive pipeline's headline claim, which could not report a lead time above ten seconds** (`_sum`/`_count` were always exact, so the *mean* was right; it is `histogram_quantile` that quietly returns the ceiling, which is worse than an error because 10.0 looks like an answer). One definition, three readers — exporter, `loadtest`, conformance — pinned by a test that asserts `Matcher::Full` really does beat the `_seconds` suffix in rendered output rather than trusting a third-party enum's variant order. Two smaller repairs finish the pass: the disarmed-budget rule stopped inferring "switched off" from `absent()` and now reads an explicit `usage_token_budget_enabled` gauge published *before* the disabled-path return (generalised as **engineering conventions §15b, "declare your arming state"** — `absent()` also fires on a renamed metric or a relabelled job, and an alert that infers a fact from a missing series is the same mistake as one that cannot reach its threshold), and `loadtest`'s latency budgets became a `LatencyBudget` newtype validated inside `Deserialize`, so an off-ladder budget can no longer be *parsed* rather than being caught by a `validate` call somebody has to remember. **This item stays open**: the load test drives the chain and the API only, so nothing in the simulation, embedding, clustering, copilot or notification groups is measurement-backed — they rest on exported gauges and structural conditions, and say so — and the staging run at 1.5× peak on real hardware is still the exit gate.
- [ ] **Screening API critical-path SLO:** the synchronous `/screen` decision (§11) sits inline on customer withdrawals — a hard **p50 < 100ms** / bounded p99 budget *under load*, dedicated rate limits + payload caps, and **graceful degradation** (serve a stale-but-flagged cached score rather than block the customer's path if intelligence is slow). It is the one API surface where latency is contractual, not aesthetic.
- [x] **Load testing** at target throughput (2026-09-07): chain tps, peak alert volume, API qps — and, first, **an instrument capable of failing.** The < 1s claim had no series behind it: the only latency detection exported was `detector_detect_duration_seconds`, one `detect` call, microseconds on a header-only block and *arithmetically unchanged* by a queue building up in front of it. `deploy/prometheus-rules.yml`'s `FastPathLatencyHigh` was reading exactly that series, so the alert guarding the platform's headline number could not fire on the failure it names — blocks backing up behind detection would have left it green while alerts arrived seconds late. So [`detection::metrics::FAST_PATH_SECONDS`](crates/detection/src/metrics.rs) now measures the span the claim is actually about — `BlockAssembled.occurred_at` → the alert's durable publication, **across the broker hop and the scheduler's bounded work channel** — split into `detection_queue_wait_seconds` (the backpressure term) and `detection_block_process_seconds` (the work), so a breach says *which* term grew. The clock is anchored to the producer's timestamp, not to receipt; a `BlockReverted` deliberately carries none, because it publishes nothing and timing it would fill the SLO series with samples that can never breach it. [`crates/loadtest/`](crates/loadtest/) offers the load and reads it. Four decisions are the whole test: **blocks are stamped with the time they were *due*, not the time they were sent** — a generator that slows down when the broker does is coordinated omission, and it reports the latency of a system under light load; the run **drains before measuring**, because the blocks still queued when the load stops are precisely the slowest ones and scraping at that instant reports the p99 of the subset that kept up; the window is a **difference of two scrapes**, so a long-lived service's healthy idle history cannot dilute a breach; and the verdict is **three-way** — `0` held, `1` breached, `2` undecided — because a load test has more ways to be uninformative than to fail (an unloaded system, an undrained pipeline, too few alerting samples, a threshold off the bucket ladder) and every one of them yields a clean-looking p99. A bucketed quantile is treated as a **bound, not a point**: with a boundary at exactly 1.0 the claim is decidable without interpolating, and a budget with no boundary is rejected when `slo.json` loads rather than turning every future run silently inconclusive. Load lives in reviewable `profiles/*.json` (each carrying its own derivation, printed with the report); budgets live in `slo.json` with **no `--update` flag** — unlike a backtest baseline, < 1s is a published claim about the product, not a record of what the code does. `just load-test` / `load-test-headroom` (the exit gate's 1.5×), nightly [`load-test.yml`](.github/workflows/load-test.yml) where **exit 2 fails the job**, runbook [`docs/runbooks/load-test.md`](docs/runbooks/load-test.md). *The limits are printed with every result, not buried here:* blocks are **header-only** (§6), so this measures the pipeline at chain rate and not the per-transaction cost of a full bundle; the alerting share is produced by `demo-v0.1`'s even-block rule rather than real evidence, so the emit/publish path is exercised at volume but no detector's *analysis* is; the span excludes ingestion's own source→emit time; and it is a cross-process wall-clock comparison, so it inherits any skew between the two. A transaction-carrying source is what retires the first two. **First measured result (2026-09-07, `mainnet-peak`, 4 blocks/s / 1001 declared tps / 1200 alerting samples / 100 API qps, everything co-resident on one dev host):** the fast path **held at 0.9992** — 99.92% of samples at or below one second, i.e. right on the boundary — and the number is the point. The *same profile with the API idle* measured a p99 bound of **250ms** with 2.5ms of queue wait; with the API loaded on the same box, queue wait went to **500ms** and the fast path to **1.000s**. A 4× degradation, landing exactly on the published budget, driven entirely by contention the fast path does not control — and completely invisible to `detector_detect_duration_seconds`, which is what the alert used to watch. The API's own checks breached in that run (success 0.883 on event-store 5xx under load; p99 share 0.974 against a 500ms budget). **None of this is a production capacity claim** — five services and the generator sharing one laptop's cores is far worse contention than separate pods, and the run's value is that the instrument now moves at all. The staging run at 1.5× peak on real hardware is the exit gate; this is the proof that the gate can fail.
- [ ] **Autoscaling:** simulation worker pool on `sim.jobs` queue depth (the designed backpressure signal, §7, §20); HPA on detection/api by CPU/qps.
- [ ] **Intelligence write-path sharding** by address range (§20); read-path gRPC scaling; cache hit-rate targets + stampede protection on the Redis hot path (§8).
- [ ] **Capacity plan:** partition counts, shard counts, storage growth for the append-only event store (it grows forever — model the cost).

**Exit gate:** SLOs met at 1.5× projected peak load in staging; autoscaling demonstrated; load test is a recurring CI/nightly job.

## Hardening Epic E — Model governance & data quality

**Goal:** detections and scores are accurate, regression-gated, and defensible.

- [x] **Backtest harness as a CI gate** (§18): wired in `.github/workflows/pr.yml` (*Backtest P/R gate*). A PR fails if any detector drops below `crates/backtest/baseline.json`, or if an `Active` detector sits below the `crates/backtest/promotion_gate.json` floor. Baselines move only via `just backtest-update-baseline`, as a reviewed diff.
- [ ] **Gate keyed on the full `(id, version, config_hash)` triple** (§18): today `baseline.json` and `model_performance.json` key on detector **id alone**, so a config change that moves precision is not distinguishable from a regression of the same detector.
- [ ] **Fixture set adequate to support an FP-rate claim** (§18): the gate currently replays 8 curated fixtures (7 scenarios + 1 clean block) at precision 1.0. That is a regression signal, not a field measurement — a single negative block cannot resolve the < 4% FP target. Needs adversarial negatives and replayed mainnet windows before the README's target can be stated as a result.
- [ ] **Shadow / A-B detector deploys** (§6 model registry already supports this) + one-click rollback via `deprecated_at`.
- [ ] **False-positive feedback loop** wired to the FP-rate panel (§19); track it as an SLO.
- [ ] **Sanctions freshness SLA:** OFAC/EU lists ingested within a bounded window; `SanctionHit` is a hard alert (§8.5) — staleness is a compliance failure.
- [ ] **Risk-score explainability audited:** every `delta` carries an `evidence_ref` (§8.3); "taint-by-association" documented as reduced-confidence, legally-contested (§8.3).
- [ ] **ML model provenance (§20):** every deployed model artifact is hash-pinned in the registry (`artifact_hash`, `feature_version`); serving/training feature-version skew is a boot failure, not a silent accuracy decay; retraining walks the same Shadow → backtest → Live gate as any detector change — no weight hot-swap path exists.
- [x] **Drift monitoring as an SLO (§20.5, 2026-08-27; hardened 2026-08-28):** `inference::DriftEngine` — a second decorator over the serving seam, wrapping `ObservedEngine` so the inference-latency histogram the < 1s budget is checked against stays free of bookkeeping — folds every served `FeatureVector` into a window and measures it against the same `ml_features::FeatureBaseline` the anomaly explanations are written from. **Windows are dual-bounded** (N vectors *or* T elapsed, never below `MIN_WINDOW`): count decides how good a reading is, age decides how soon there is one, and count-only left a block-granularity model blind for ~100 minutes after every deploy. **Drift is durable, not just a gauge:** a breaching window publishes `ModelDriftDetected` into the event store carrying the drifted features and the exact `(id, version, config_hash)` triple that was serving, so an incident review months later can ask which weights were live — the audit question Prometheus retention cannot answer. Emission is the scheduler's, on the block boundary, through `inference::DriftSource` → `detection::DriftPublisher` (arch-conformance forbids `inference` a broker edge, and a detector is a pure fn), reusing the existing producer/retry/DLQ. Metrics: `model_feature_drift{model,feature}`, `model_drift_max{model}`, `model_drift_threshold{model}` (**the alert rules compare against this gauge, not a literal — a PromQL constant would be a second definition of a per-model policy**), `model_drift_breaches_total`, `model_drift_windows_total{closed_by}`, `model_drift_rejected_total` (serving-time §20.5 skew, pages), `model_drift_skipped_total{reason}`, `detection_drift_events_total`. Alerts: `ModelFeatureDriftHigh`, `ModelFeatureDriftSevere` (2.5x a deployment's own threshold), `ModelServingSkew`, `ModelInferenceFailing`, `ModelDriftMonitoringSilent` and `ModelDriftObservationsDropped` (**monitoring the monitor** — a stalled monitor and a model with no drift render identically, because a gauge holds its last value), plus per-detector `DetectorLatencyBudgetExceeded` (§17) and the `detector:hit_rate:ratio_rate1h` recording rule; dashboard `deploy/grafana/dashboards/model-serving.json`. The monitor **fails open and says so**: `try_lock`, poison recovery rather than latching off, a bounded pending queue, every dropped observation counted by reason (generalised into engineering-conventions §15). **Thresholds are shipped defaults on the statistic's own scale, not calibrated SLOs** — no production traffic exists to tune against; they are per-model config and reach the alerts through the exported gauge. The statistic is frozen by an `insta` snapshot, since every deployed threshold and every stored event is denominated in its units. Still open: the registry is deliberately *not* mutated at runtime (it is boot-immutable so a triple means one thing for a process's whole life); the response to sustained drift is `deprecated_at` or a new version.
- [x] **LLM output governance (§20.4, Sprint 20 t1/t3/t4/t5, 2026-08-29 → 2026-08-31):** every clause of this item is now a mechanism with a test, not a practice. **The seam cannot become a fact-producer.** [`crates/llm/`](crates/llm/) owns transport, retry, admission and token accounting and nothing else; arch-conformance ([`crates/arch-conformance/src/lib.rs`](crates/arch-conformance/src/lib.rs)) fails the build if it gains an `intelligence`/`rule-engine`/`simulation`/`sqlx`/`redis`/`clickhouse`/`rdkafka`/`lapin` edge, and the `copilot` rule is its **mirror image** — it must reach the model *through* `llm` and must not depend on `event-store`/`clickhouse`/`intelligence`/`detection`. That pairing is the whole safety argument as a graph property: a validating boundary lives structurally **above** the seam that produces what it validates, so "an LLM output is a proposal, never a fact" cannot be weakened by a refactor that merely compiles. **Drafts are their own event types, and carry references rather than prose.** [`events::copilot`](crates/events/src/copilot.rs) / `EventFamily::Copilot`: `IncidentNarrativeDrafted` carries `narrative_ref` (`copilot://drafts/{id}`) plus the provenance triple (responding model, prompt id/version/digest) — an unapproved machine-written document is never replicated into the immutable audit log — while `RuleDraftProposed` carries the compiled *definition* (a closed structure that already passed the compiler) and only the **hash** of the customer's sentence. No LLM output is detection evidence, and no path from a completion to the graph exists. **Citations are enforced at landing, not requested in a prompt.** [`copilot::grounding`](crates/copilot/src/grounding.rs) parses the inline `[uuid, …]` citations back out of the drafted text and **narrows** `grounded_event_ids` from the window the model was shown to what the text actually cites; `no_claims` / `uncited` / `fabricated` (an id the model was never shown — the dangerous one, because it looks verifiable until someone looks it up) land the draft **`blocked`, never `ready`**, the same statement a refusal makes. One landing rule, three writers (worker `finish`, the cross-pod cache, the batch backfill) all go through a single private `write_landing`, so a rebalance cannot promote text the worker would have blocked. The cited-ratio threshold is deliberately **below 1.0** (`COPILOT_MIN_CITED_RATIO`, 0.5) because the prompt requires uncitable sentences — a 100% bar rejects the most compliant drafts, which is how a gate gets switched off — while `reject_unknown` is intentionally **not** configurable. **The audit re-asks the question against today's store.** [`copilot::grounding_audit`](crates/copilot/src/grounding_audit.rs) re-runs `grounding::evaluate` over each landed narrative's stored text against the ids event-store returns *now*, reusing the same citation parser (a second parser would only check a second opinion of the text). Seven verdicts, and the distinctions are the product: `grounded` / `unresolved` (cited, and the store does not have it) / `drifted` (the column and the prose disagree — the column is what every consumer reads *instead of* the text) / `unchecked` (the boundary never ran — not "probably fine", unexamined) / `evidence_missing` (**a retention violation**: still inside its window, no evidence) / `expired` (retention doing its job — a pass, still counted) / `unverifiable`. Exit codes are the deliverable — `0` clean, `1` findings, `2` inconclusive — shipped as `copilot audit`, `just copilot-audit`, and a weekly CronJob with `backoffLimit: 0`; paging is a **keyset walk** because an `OFFSET` walk over a table being written to silently skips rows, and an audit that skips drafts is worse than none. Alerts: `CopilotFabricatedCitations`, `CopilotGroundingAuditFindings`, `CopilotGroundingAuditUnverifiable`, and the leading indicator `CopilotNarrativesWillOutliveTheirEvidence` — drafts that resolve perfectly today but whose oldest cited event expires *before* the draft may be destroyed, i.e. already scheduled to become undefendable. **Prompts are versioned, hashed, and change under review.** [`crates/copilot/prompts/MANIFEST`](crates/copilot/prompts/MANIFEST) pins `purpose@version  sha256` for **linked and retired** artifacts; two tests are the gate (manifest match, plus a `read_dir` sweep asserting every `.md` in the tree is described by a `PromptDescriptor`), regenerated by `just prompt-manifest`, with [`.github/CODEOWNERS`](.github/CODEOWNERS) over `prompts/**` and the three boundary modules and the rule written down as **engineering conventions §16**. Retired artifacts matter most: linked to no purpose, covered by no cache key or boot check, and the one file historical drafts are attributed to. Every draft is stamped with the prompt's id/version/digest, so a document can be re-read under the instructions that produced it. **NL-created rules cross the real parse boundary and still need a human.** `copilot::rule_draft::compile_check` runs §9's own path — `RuleDefinition` → `Rule::validate` → `CompiledRuleSet::compile` (the *compiler*, not just the validator: `validate` says well-formed, `compile` says evaluable) — and nothing in `copilot` re-implements the condition vocabulary. `CompiledDraft` is a newtype **constructible only by that function**, so a signature cannot be satisfied by the `RuleDefinition` any arbitrary bytes deserialize into, and `into_rule(id, owner)` demands the two fields the model was structurally never offered (the generated schema has no owner slot, `additionalProperties: false`). `POST /v1/rules/draft` returns **202 and creates nothing**; owner is the verified JWT `sub`, twice; activation is `server`'s `POST /v1/rules`, a customer action. A draft **kind** is one `DraftCapability` object (grounding / request / check / announce) behind a `CheckRegistry` that is **exhaustive over `DraftKind`** and fails closed — the motivating failure was that adding a kind and forgetting its answer-check was *silent*: it fell through a `match` arm, landed `ready`, and reached a customer with no boundary applied. **Prompt injection is treated as expected input:** instructions live only in the versioned system artifact, chain data is fenced as `Untrusted` in a user turn and cannot close its own fence — a reduction of reliance on, never a replacement for, the load-bearing defences above. *Still open (deliberately, and neither is this item's claim):* the audit answers **"does the cited evidence exist"**, not "does it support the claim" — the human reviewer is that boundary, and the review API is **opt-in** (`COPILOT_HTTP_ADDR` unset serves nothing), so a deployment that never sets it accumulates drafts nobody approves; and `unchecked`/`unverifiable` are reported rather than driven to zero, because retention legitimately produces the second one.
- [x] **LLM cost containment (Sprint 20 t1/t3/t5, 2026-08-29 → 2026-08-31):** **One metering path, eight SKUs.** `llm::MeteredClient` is the single call site for both the token metrics and `UsageFact::record`, published inline through the `event-bus` seam — arch-conformance *requires* that edge precisely so no LLM-specific second producer can appear (§13 has one `UsageRecorded` path, or the invoice cannot be reconciled). The quantity is split into **eight** `UsageEventType`s — input / output / cache-write / cache-read, each in a synchronous and a `LlmBatch*` variant — because the provider prices all of them differently and batched tokens bill at half rate: a single "tokens" number is unpriceable, and a mixed one is wrong. A **refusal is a successful, billable call** (HTTP 200 + `stop_reason: refusal`, real usage), so it is modelled as a `Completion`, not an `Err` — modelling it as an error would drop exactly the usage the metering path must record. **The decorator order is what makes the invoice add up:** `LlmStack` is `Cached → Metered → Retrying → Breaker → Admitted → Anthropic`, and every wrong order compiles — cache outermost so a hit costs no permit, no bill and no breaker signal; **meter above retry so three attempts are one invoice line**; admission innermost so a permit covers the HTTP call and not the backoff sleep. **The response cache is a correctness control, not an optimisation:** non-deterministic + billed + at-least-once means a redelivery produces a *second regulatory document* and a second bill, so the key folds in the customer (a collision would be a cross-tenant leak) and the prompt's content hash; across pods that cache **is the drafts row itself**. **Budget alarms are wired and answer "who" out of band.** [`crates/usage/src/budget.rs`](crates/usage/src/budget.rs) evaluates per-customer spend over `usage_rollup_daily` on a timer (`USAGE_TOKEN_BUDGET`, warn ratio, window, interval), exporting `usage_token_budget_customers{level,scope}`, `usage_token_budget_max_ratio` and `usage_token_budget_alarms_total`. `CopilotTokenBudgetAlarm` fires on the `level="alarm"` **gauge** — "is anyone over budget *now*" is the alertable question; the counter beside it says how often that has been true. **The customer id is a log field, never a metric label** (§19 — an unbounded id set has no business in a time series); `just usage-budget` runs the *same* `evaluate_now` the loop runs, which is where an operator finds out who. Nil-customer rows are watched as `scope="platform"` rather than filtered — the copilot's own narratives are the most likely runaway loop in the system — and the token SKUs are **enumerated exhaustively** (pinned by a `strum::EnumIter` walk over `UsageEventType`), not prefix-matched, because a prefix is a convention a new SKU silently opts out of. §15 throughout: `usage_budget_evaluations_total{outcome}` plus `usage_budget_last_success_timestamp_seconds` and `CopilotTokenBudgetMonitorStale`, because a monitor that quietly stopped looks identical to one with nothing to report — and until it recovers the alarm is reporting a stale number. **A runaway loop is bounded, not merely alarmed:** `llm::admission` sheds calls (`Denied::SpendCeiling`) once `LLM_SPEND_CEILING_TOKENS` is spent in `LLM_SPEND_WINDOW_SECS`, alongside `LLM_MAX_IN_FLIGHT` and a breaker that **429s never trip** (a rate limit is the most common "failure" a healthy integration sees). That ceiling is platform-wide with no customer dimension **on purpose** — a per-customer ceiling here would be request-time quota enforcement by another name, which is the Epic C item struck above. **The billing bug that shaped the batch path:** the backfill's open-batch set was derived from drafts still `in_flight`, so a batch whose results came back short stayed open forever — re-polled, re-fetched and **re-metered every lap with no sleep**. Fetch-once is now schema, not convention (`copilot_batches.results_fetched_at` claimed by a conditional UPDATE), the batch closes unconditionally so the open set strictly shrinks, and stragglers are counted (`copilot_backfill_stragglers_total` — the counter ships; an alert rule on it does not, and is the one loose end in this paragraph). A `source` column splits the queues so a synchronous worker **structurally cannot** pay full price for archive work. *Still open:* both ceilings **ship dark** — `USAGE_TOKEN_BUDGET` and `LLM_SPEND_CEILING_TOKENS` default to `0`/unset and are not set in [`deploy/k8s/`](deploy/k8s/), so enabling them is a deploy-time act, not a property of the code; the rollup the budget reads is **approximate** by design (exactness would mean a full scan on a timer, and the module says so); the spend ceiling and in-flight limiter are **per-process**, while the provider's limit is org-wide — a real org budget needs the shared Redis `CallAdmission` the seam is already object-safe for; and everything here is denominated in **tokens, not currency** — there is no price table in the repo, so "surprise invoice" is bounded in the unit the provider bills, one conversion away from the number a finance team reads.

**Exit gate:** no detector ships without a passing backtest; FP rate within SLO; sanctions freshness monitored; no ML artifact deployed outside the registry; grounding audit green.

## Hardening Epic G — Compliance & legal (this product specifically)

**Goal:** survive the questions a regulated customer's legal team will ask.

- [ ] **Audit-trail completeness guarantee** documented and tested — the §4 "complete, reproducible answer to *why did you alert?*" must be literally true.
- [ ] **Data retention vs. erasure tension:** an immutable, append-forever event store (§4) collides with right-to-erasure regimes (GDPR). Decide and document: is an on-chain address personal data in your jurisdictions? Crypto-shredding / pseudonymization strategy for any PII that does enter (customer accounts, webhook URLs, emails in §12/§13). **This is a genuine, easy-to-miss production blocker — resolve before selling to EU customers.**
- [ ] **Label dispute / correction workflow:** someone *will* contest a `KnownScammer` label. Conflicting labels are already retained (§8.1); add a documented dispute and override process.
- [ ] **Alert liability:** terms of service framing provisional alerts (§6) so a wrong/retracted alert isn't actionable against you.
- [ ] **Screening-decision liability & governance:** a `block` from the Screening API (§11) is a *blocking action* — a denied withdrawal — not a passive alert, so it is the highest-liability surface in the product. The decision policy must be **versioned** (record which policy + version produced each block, for dispute), every `block`/`review` must carry its `evidence_ref` factor breakdown (explainable, §8.3), there must be a documented **override / appeal path** for a contested block, and ToS must frame the decision as advisory input to the customer's own action — not our determination. Screening decisions are themselves logged to the access-audit trail.
- [ ] **Billing-meter accuracy:** you charge on `UsageRecorded` (§13) — metering must be exact and reconcilable; under/over-billing is a trust and legal issue.
- [ ] **SOC 2 readiness** if selling to enterprise (follows naturally from Epics B, C, F).

**Exit gate:** retention/erasure policy signed off by legal; audit completeness test green; metering reconciliation proven.
